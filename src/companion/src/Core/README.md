# Companion Core: craft history contract

Core owns **C01 Craft History Model** and **C02 History Reconciliation** from the Companion epic (#38). It does not parse Lua, write SavedVariables, compute addon historical rollups, use a database, or access remote storage.

## Canonical grains

- `CraftObservation`: **one completed crafting attempt**, not necessarily one output callback, request, or crafting session.
- `CraftReagent`: **craft × item ID**. Input allocation and Resourcefulness returns are separately nullable. Allocations are integer quantities; returned quantities use `decimal` to retain legacy fractional SavedVariables observations. Duplicate item slots must be folded by the SavedVariables adapter, with missing measurements preserved as unknown.
- `CraftOutput`: **craft × output item ID × quality**, with a nullable quality and positive quantity. Supports operations generating multiple output items.
- `CraftDimensions`: metadata keyed by stable WoW item/recipe/profession IDs and profession expansion keys and the addon's project/region/realm/GUID character key. Display names are enrichment, not identities.

`null` measurements mean *not observed*. `false` or `0` mean explicitly observed negatives or zeros. Likewise, a null reagent/output collection means its complete contents were not observed, while an empty collection means it was explicitly observed empty. We do not store historical addon aggregates in Core.

The recorder's current persisted crafts expose recipe/output IDs, output quantity/quality, timestamps, operation IDs, concentration spent/currency, ingenuity proc/refund, multicraft bonus, Resourcefulness outcome/completeness, and input completeness. `InputsComplete` and `ResourcefulnessComplete` preserve the addon's explicit completion distinctions; null is unknown and false means known incomplete. The source also contains request/allocation, reagent and dimension tables. The SavedVariables adapter resolves those links and collapses slot-level reagent detail to the agreed craft × item grain. These fields may be absent from individual records; not all crafts can have all measurements reconstructed.

## Game context and expansion classification

Each canonical `CraftObservation` has a **required** `GameContext(GameProject Project, string? ProgressionTrack)`. `GameProject` is an int-backed open enum of Blizzard project IDs, including Retail, Classic and Forever; a future positive numeric project ID remains representable. `ProgressionTrack` optionally identifies a distinct realm/ruleset history within the same game project (for example Classic Era versus Hardcore). It is **not an expansion** and must be established from trustworthy source context rather than guessed.

`ProfessionExpansionKey` is a separate **optional** craft classification, for filtering Retail Midnight crafts separately from Dragonflight crafts recorded in the same Retail game. Unknown classification stays null; it must not be inferred from the craft timestamp or assumed to be the current expansion. It is not a requirement for Classic or Forever to expose Retail-style profession divisions.

All character/item/recipe/profession/expansion **dimension keys are scoped by `GameContext`**, including numeric Blizzard IDs, so a recipe ID reused by Forever cannot be accidentally merged with the Retail recipe of the same number. Same craft identity with contradictory game contexts is a conflict, not an automatic move. Source adapters must establish the context before promoting imported crafts into canonical history; background imports may run for multiple contexts, but analytical queries must be restricted to **one selected context**, with optional profession expansion filtering.

## Identity and provenance

`CraftIdentity(Origin, Observation)` denotes a craft's durable identity in a **provenance namespace**. Its two strings are a model contract, **not proof that an imported legacy ledger has globally unique craft IDs**.

In the current addon, craft, request, session and some dimension IDs are scoped to a ledger. Copying a SavedVariables file onto two devices and recording independently can reuse local IDs. `gameOperationId`, timestamp, character and recipe are useful evidence but are **not guaranteed globally unique identity keys**. Assigning new IDs independently to every imported copy would also duplicate shared history.

An adapter must either:
1. Use an authoritative, durable source-assigned craft ID that survives file copying (ideally newly generated by WoW Core, with correct capture lineage); or
2. Supply documented lineage/collision evidence and **surface unresolved identities as conflicts**. It must not silently guess by timestamp, local craft ID, operation ID, or source computer alone.

Adding durable source-assigned IDs to the WoW addon is a likely future contract change. Core intentionally does not simulate a solved source identity problem.

## Reconciliation

- Idempotent union of disjoint craft identities.
- Same identity + compatible partial observations: retain known fields and enrich unknown ones.
- Same identity + contradictory known values (including changed recipe, source provenance, timestamp or outputs): record conflicts.
- Reagents are matched by item; independently unknown input and return quantities can be enriched. Different observed reagent-item sets are conflicts unless a set is wholly unknown (`null`).
- Outputs are matched as a complete observed set (item, quality, quantity). We do **not** union output sets from separate observations of uncertain completeness.
- Dimension metadata is reconciled by stable ID; optional display labels are chosen deterministically; contradictory known semantic relationships (e.g. recipe → profession) are conflicts.
- **Never persist a failed merge.** `CraftHistoryReconciler.Merge` returns `History = null` when it cannot produce an unambiguous combined history.
- Never merge or sum addon `craftSeries`, `resourcefulnessSets`, `returnedReagents`, or other precomputed rollups. The SavedVariables adapter derives supported rollups from craft observations after reconciliation.

We do not interpret a known-to-known contradiction as a newer authoritative correction without a source-provided revision/order contract. Doing so would turn arbitrary input ordering into last-write-wins. Repaired missing data (unknown → known) works today.

## Validation and limitations

Use `CraftHistoryValidator` before import and after reconciliation. Dimension labels may be partial; their absence does not invalidate a craft. Catalog references, when present, must use valid IDs and unique keys.

A companion can regenerate rollups from **crafts it has actually recorded**. If the addon pruned a craft *before it was ever imported*, aggregate-only evidence cannot reproduce the missing individual observation. Core will not fabricate it.

The separate SavedVariables project will own format-specific migrations, parsing, serialization, and generation of the addon's bounded detailed ledger and historical rollups; Storage will own authoritative OLAP persistence.
